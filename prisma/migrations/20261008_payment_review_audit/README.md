This additive migration preserves operator rejection time, identity and full reason on refunds and withdrawals. It must sort after `20261008_payment_ledger`, which creates the tables. No business rows or money values are rewritten. The already-applied payment ledger SQL is unchanged.

The dedicated loopback PostgreSQL was upgraded and its migration status and full Prisma schema diff verified. `test/integration/funds-ledger.test.ts` also applies all four migrations, in sorted order, to its new, randomly named disposable schema. Cleanup is restricted to that schema and never touches a cloud database or existing business fixtures.

Funds use integer cents and keep the legacy Float balance as a derived compatibility mirror on debits. The wallet invariant is `openingBalanceCents + sum(non-LEGACY income amountCents) = balanceCents`; available funds are `balanceCents - frozenBalanceCents - nonWithdrawableBalanceCents`. Refunds and withdrawals reserve through an atomic predicate on the same angel row. Mock and unverified legacy balances are never eligible for real outflow.

Verified event metadata is committed before financial processing; no raw provider payload or openid is stored in the inbox. A failed application remains `RETRY`, and the provider must retry notifications when the HTTP handler fails. Pending funds also reconcile through a newly verified provider query. Historical `RETRY` metadata is retained for audit and is not replayed without its original provider facts; a successful compensating query settles the financial record without fabricating or rewriting the old event. Provider IDs are checked again while the financial record is locked.

If a transfer create response is lost before `package_info` is saved, a query in `WAIT_USER_CONFIRM` cannot reconstruct the confirmation package. The withdrawal stays `UNKNOWN` with funds frozen and `CONFIRM_PACKAGE_UNAVAILABLE`; no second transfer is created. A controlled provider-supported recovery is required. Merchant/AppID configuration must not be rotated while pending transfers remain unresolved.

This is local migration and contract evidence, not permission to run migrations against an existing cloud database. Before any production upgrade: back up, confirm restore, compare actual schema and migration history, and follow the ledger migration rollout requirements. Do not reset or baseline an existing database merely to make migration commands succeed.
